## 第一轮为何不能验收

会话：`session-20261119-130643-KQgO`。
原始数据：`live-check-20261119-130643-nrO7/raw`。

用户移动约一米并回到原位置与朝向，但建图在移动期间遇到时间异常并暂停，冻结的位姿不能用于回程评估。

按消息写入 id 顺序检查原始数据，IMU 消息时间与 rosbag 接收时间共同倒退两次：约 -0.416592 秒、-0.409352 秒。只按时间戳排序会掩盖这个问题，所以审计使用消息 id 顺序。

对应两帧点云分别积累了 104,352 和 101,568 个点，逐点时间偏移最大约 4.294 秒。驱动原先同时用可回拨的主机时钟给数据打时间戳、决定点云发布时机；时钟回拨会暂停发布并使部分负时间差转为无符号大数。具体由哪个主机校时组件触发回拨尚未确认。

诊断时曾并行读取仍在写入的 SQLite 数据库，触发数据库锁冲突，录制器异常退出。这是诊断操作造成的问题。原数据库已保留，停止写入后执行 reindex 恢复 metadata。现已禁止审计未完成的录包，并为现场监测增加录制器退出检测；后续必须先结束录制、确认 metadata 完整，再分析。

## 修改范围

仅修改 Livox 驱动的 `src/comm/pub_handler.cpp` 和 `pub_handler.h`：

- 无同步模式的 LiDAR 和 IMU 共用一次锚定到系统 epoch 的单调计时器，之后的相对时间来自 steady_clock。
- 无同步模式的点云发布调度也改用 steady_clock。
- PTP/GPS 时间戳分支保留。
- FAST-LIO 的时间异常暂停保护保留，未通过放宽保护掩盖倒退。

备份：`driver-clock-backup-20261119`。
补丁：`Livox_monotonic_clock_20261119.patch`。
测试：`test_driver_clock.py` 从实际源码提取时钟类，模拟两次已观察到的回拨及向前跳一小时，全部通过。没有更改系统时间或全局时间同步设置。驱动重新编译成功，有原有 unused variable 警告。

该方案保护当前无同步雷达的内部相对时间，不等同于外部 PTP 同步。若主机系统时间再次调整，输出时间与新的墙钟时间可能有偏差；后续接相机或飞控时仍需统一时间基准。

- 地图保存服务成功，`session-20261119-131656-bmeW/map.pcd` 包含 317,651 个点，坐标全部有限，空间范围无发散级异常。
- 录制器正常退出并生成 metadata；完整性分析在结束之后对数据库副本进行，没有并发读取活动数据库。

本轮约一米移动完成验证。更大房间范围、长时间运行、相机同步和飞控接入仍未验收。
